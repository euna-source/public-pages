01바로 쓸 설정

바로 쓸 설정

릴스 렌더(HyperFrames 0.8.208 기준, 0.8.211 출시 뒤 다시 잰다)

  • 미리보기: HYPERFRAMES_NO_TELEMETRY=1 npx hyperframes render . -w 1 -q draft
  • 출고: HYPERFRAMES_NO_TELEMETRY=1 npx hyperframes render . -w 1 -q high --keyframe-interval 2 --max-bitrate 8M 뒤 ffmpeg -i in.mp4 -c copy -movflags +faststart out.mp4, ffprobe로 yuv420p·30fps 확인
  • 폰트: pyftsubset NotoSansCJKkr-Bold.otf --text-file=자막.txt --flavor=woff2, 타임라인은 document.fonts.load(...) 뒤 등록
  • --gpu는 0.8.208에서 쓰지 않는다(캡처 뒤 순차 인코딩·고정 비트레이트). 미출시 PR #6631이 고친다.
  • 렌더 전 npx hyperframes check --json 오류 0, 큰 수정은 snapshot --review, 작은 수정은 snapshot --at

c8c-web 홈페이지 전(파일 경로는 5/13 사본 기준)

  • 앱 루트 <MotionConfig reducedMotion="user">, GSAP 쪽은 gsap.matchMedia('(prefers-reduced-motion: reduce)')
  • src/components/BounceProvider/index.tsx: setY 상태 대신 useMotionValue + style={ { y } } + 놓을 때 animate(y, 0, spring)
  • will-change 상시 15곳 해제 또는 animationend에서 해제, 팝업 backdrop blur 60px → 20~24px 비교, PopoverModal을 AnimatePresence로 감싸 exit 복구
  • height·width·transition: all 5곳은 transform·layout으로
  • motion ^11.18.1 → 14.7.1 이상 고정, import는 motion/react. v13부터 @emotion/is-prop-valid 자동 사용이 빠지지만 styled(motion.x)가 없어 영향은 작다(빌드로 확인)
  • 스크롤 장면: @supports (animation-timeline: view()) { animation-timeline: view(); animation-range: entry 0% cover 30%; }, 미지원이면 처음부터 보이게
  • 영상 자리: poster 50KB 안팎(AVIF/WebP), 화면 밖 영상 preload=none, AV1 → H.264 순 <source>

02영상 렌더 파이프라인

영상 렌더 파이프라인

우리 15초 릴스에서 병목은 인코딩이 아니라 헤드리스 Chrome 프레임 캡처다. 10/27 로그를 보면 캡처 46.2초 동안 인코딩이 함께 돌아 끝났다. 이 M2 Pro에서 시험해 보니 워커를 늘리면 오히려 느려졌는데, 빠른 drawElement 캡처 대신 스크린샷 캡처로 바뀌기 때문이다. --gpu도 이득이 없었다. 다만 --gpu의 수치(1분 54초)는 기준선 재측정이 중단돼 미확정이다. 그래서 단일 워커와 drawElement 조합을 유지하고, 화질은 비트레이트 여유·closed GOP·faststart로, 안정성은 폰트 서브셋과 선로드로 챙기는 것이 가장 효과가 크다.

  1. HyperFrames 0.8.208 render는 다음 옵션을 제공한다. --workers(1~8, 기본 auto, 워커마다 Chrome 프로세스 하나에 약 256MB), --gpu, --browser-gpu, --experimental-fast-capture, --frames-cache-dir, --resume·--keep-segments(HF_SEGMENTED_CAPTURE=true일 때만), --batch·--batch-concurrency, --low-memory-mode, --docker. 로컬 설치본의 render --help로 확인했다.
    • 적용: 릴스 시험 폴더에서 npx hyperframes benchmark --runs 3 --json을 돌려 이 Mac에 맞는 fps·quality·워커 조합을 수치로 고정한다.
    • 출처: 로컬 CLI: hyperframes render --help (v0.8.208), https://hyperframes.heygen.com/guides/rendering · 2026-10-27 설치본 기준(문서 페이지는 날짜 미상) · 확신 high
  2. 10/27 렌더는 --workers 1(명시), standard, drawelement 캡처, 스트리밍 인코딩으로 47.6초 걸렸다(캡처 46.2초, 인코딩은 캡처 중 동시 진행). 2026-10-28에 같은 컴포지션을 다시 돌리니 --workers 4는 2분 4.1초, auto(3워커)는 1분 35.0초였다. 두 경우 모두 스트리밍 인코딩이 꺼지고 screenshot 캡처로 바뀌었다.
    • 적용: 릴스 렌더 스크립트에 --workers 1을 고정하고, 로그에 'drawelement capture'가 찍혔는지 확인하는 한 줄 검사를 넣는다.
    • 출처: 로컬 측정: 릴스 시험 폴더/render.log, 벤치 로그/*.log · 2026-10-27·2026-10-28 측정(같은 시점 기준선 재측정은 미완) · 확신 medium
  3. HyperFrames --gpu는 macOS에서 h264_videotoolbox를 쓴다. CRF는 쓰지 않고 품질별로 고정 비트레이트를 정한다(quality 15 이하 0.24bpp, 18 이하 0.16bpp, 그 외 0.08bpp, -allow_sw 1). 1080x1920 30fps의 standard 설정이면 약 10Mbps다. 2026-10-28 시험에서 --workers 1 --gpu는 1분 54.2초 걸렸고 파일은 4.0MB였다.
    • 적용: 릴스 렌더에서는 --gpu를 쓰지 않는다. VideoToolbox는 긴 영상이나 FFmpeg 후처리 재인코딩에만 -c:v h264_videotoolbox -b:v 12M처럼 비트레이트를 명시해 쓴다.
    • 출처: 로컬 소스 node_modules/hyperframes/dist/chunk-MPO25DQW.js buildVideoToolboxRateControlArgs, 측정 벤치 로그/workers1gpu.log · 2026-10-28 확인 · 확신 medium
  4. Apple Silicon의 h264_videotoolbox가 libx264보다 2.6~4배 빠르다는 보고가 있다. 다만 같은 파일 크기에서는 libx264 화질이 낫고, -crf가 듣지 않아 -b:v나 -q:v로 제어해야 한다. 근거는 2021년 포럼 보고뿐이고, 2025년 이후 벤치마크는 찾지 못했다.
    • 적용: 출고본은 libx264 slow·CRF 15~16 계열(HyperFrames -q high)로 뽑고, VideoToolbox는 미리보기용으로만 쓴다.
    • 출처: https://ffmpeg.org/pipermail/ffmpeg-user/2021-October/053727.html , https://developer.apple.com/forums/thread/678210 · 2021-10(포럼) — 2025-06 이전 자료, 최신 대조 실패 · 확신 low
  5. HyperFrames 품질 프리셋은 draft(ultrafast, CRF 28), standard(medium, CRF 18), high(slow, CRF 15)이고 기본값은 looks(CRF 16)다. 10/27 렌더는 standard로 뽑았고, 결과 비트레이트는 약 340kbps(622.6KB/15초)였다.
    • 적용: 작업 중 확인은 -q draft로, 최종 출고는 -q high --keyframe-interval 2 --max-bitrate 15M로 나눈다.
    • 출처: 로컬 소스 chunk-MPO25DQW.js 9917~9919행, render --help · 2026-10-28 확인 · 확신 high
  6. Meta 공식 Reels 규격은 다음과 같다. 컨테이너는 MOV/MP4(edit list 없음, moov atom은 파일 앞쪽). 코덱은 HEVC 또는 H.264(progressive, closed GOP, 4:2:0). 23~60fps, 가로 최대 1920px, VBR 최대 25Mbps, 오디오는 AAC 48kHz·128kbps. 길이 3초~15분, 크기 300MB 이하이며 9:16을 권장한다. 영상 색공간 항목은 없고, 커버 이미지만 sRGB로 명시돼 있다.
    • 적용: 출고 직전 ffmpeg -i in.mp4 -c copy -movflags +faststart out.mp4로 moov를 앞으로 옮기고, ffprobe로 yuv420p·bt709·30fps·GOP 2초를 확인한다.
    • 출처: https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/media · 날짜 미상 · 확신 high
  7. HyperFrames --resolution portrait-4k(2160x3840)는 DPR을 올려 슈퍼샘플링하는 옵션이다. 그런데 Meta Reels 규격은 가로 최대 1920px라 이 해상도는 규격을 넘는다.
    • 적용: 릴스는 1080x1920으로 유지한다. 선명도는 해상도 대신 CRF·비트레이트와 글자 획 두께(700 굵기 이상, 외곽선·그림자)로 확보한다.
    • 출처: render --help(--resolution), https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/media · 2026-10-28 확인 / 날짜 미상 · 확신 medium
  8. HyperFrames의 빠른 캡처(drawelement)는 Chrome HTML-in-Canvas API의 drawElementImage를 쓴다. macOS와 하드웨어 GPU 조합에서 기본으로 켜진다. PSNR 자기검증(10/27 로그 55.7dB)에 실패하면 Page.captureScreenshot으로 자동 후퇴한다. 이 API는 Chrome 148부터 origin trial이고, 150·155에서 호환이 깨지는 변경이 있었다.
    • 적용: HyperFrames와 번들 Chrome 버전을 package-lock으로 고정한다. 업그레이드 뒤에는 로그의 captureMode와 렌더 시간을 다시 잰다.
    • 출처: https://developer.chrome.com/blog/html-in-canvas-ot-changes , https://groups.google.com/a/chromium.org/g/Blink-dev/c/t_nGEmJ_v4s · 2026-04(Intent to Experiment)~2026 중 블로그(정확한 날짜 미상) · 확신 medium
  9. CDP HeadlessExperimental.beginFrame과 virtual time은 새 headless 모드에서 지원되지 않고 chrome-headless-shell에서만 쓸 수 있다는 Chromium 측 답변이 있다(2024-11). HyperFrames는 시각을 frame/fps 정수 계산으로 seek한다. 그리고 Date.now·requestAnimationFrame·시드 없는 Math.random을 금지하는 방식으로 결정론을 확보한다.
    • 적용: 컴포지션에 rAF·setTimeout·CSS 무한 애니메이션을 쓰지 않고, 모든 모션을 paused GSAP 타임라인에 올린다. 렌더 전에 npx hyperframes check를 통과시킨다.
    • 출처: https://groups.google.com/a/chromium.org/g/headless-dev/c/QBQEm5Yd3_E , https://hyperframes.heygen.com/concepts/determinism · 2024-11(2025-06 이전, HyperFrames 현행 문서로 부분 대조) / 날짜 미상 · 확신 medium
  10. HyperFrames는 캡처 전에 문서의 모든 img에 decode()를 걸고 document.fonts.ready를 기다린다. 하지만 fonts.ready는 이미 요청된 폰트만 기다린다. 그리고 우리 컴포지션은 17MB짜리 NotoSansCJKkr-Bold.otf 전체를 @font-face(font-display:block)로 싣고 있다.
    • 적용: pyftsubset NotoSansCJKkr-Bold.otf --text-file=자막.txt --flavor=woff2로 쓰는 글자만 서브셋한다. 타임라인은 document.fonts.load('700 1em "Nana Korean"','가')가 끝난 뒤 만들어 window.__timelines에 등록한다(HyperFrames lint 권고).
    • 출처: 로컬 소스 chunk-7PAK7LZ5.js waitForLateSubresources, chunk-FC4WT5FX.js lint 메시지, 릴스 시험 폴더/index.html · 2026-10-28 확인 · 확신 medium
  11. Remotion은 v4.0.228부터 hardwareAcceleration('disabled'|'if-possible'|'required')을 지원한다. macOS VideoToolbox 전용이고, 공식 문서 기준으로는 ProRes만 되며, CRF를 쓸 수 없고 Lambda·Cloud Run에서는 지원되지 않는다. v4.0.397부터는 @remotion/web-renderer의 renderMediaOnWeb으로 브라우저에서 mp4(h264+aac)·webm을 렌더할 수 있다. 내부는 Mediabunny·VideoFrame 기반으로, WebCodecs 계열로 보인다.
    • 적용: 릴스 파이프라인은 HyperFrames를 유지한다. 브라우저 클라이언트 렌더가 필요해지면 그때 Remotion 라이선스 견적과 함께 renderMediaOnWeb을 검토한다.
    • 출처: https://remotion.dev/docs/hardware-acceleration , https://www.remotion.dev/docs/web-renderer/render-media-on-web · 날짜 미상(버전 표기만) · 확신 medium

    • 적용: 변형이 많으면 먼저 로컬 --batch rows.json --batch-concurrency 2로 처리하고, 하루 수백 개 단위가 될 때만 lambda를 검토한다.
    • 출처: 로컬 CLI hyperframes --help (v0.8.208), https://github.com/heygen-com/hyperframes/pull/658 · 2026-10-28 확인 / PR 날짜 미상 · 확신 medium

웹 애니메이션 성능 기술

C8 홈페이지 버벅임을 줄이는 1순위는 transform·opacity(필요하면 filter·clip-path)만 애니메이션하고 높이·위치·그림자 애니메이션을 걷어내는 것입니다. 2순위는 motion을 v11에서 v14로 올리는 것으로, React 18을 계속 지원하고 14.2부터 x·y 같은 개별 transform이 하드웨어 가속되며 LazyMotion으로 번들을 줄일 수 있습니다. 2026-10 기준 같은 문서 View Transitions·@starting-style·linear()는 3대 브라우저 모두 지원하고, CSS 스크롤 애니메이션은 Firefox가 159(10/27 배포)에서 기본으로 켜겠다고 예고했으며(출시 반영은 미확인), 문서 간 View Transitions는 Firefox가 부분 지원이라 점진 향상으로만 씁니다.

  1. 합성 단계에서만 처리되는 transform·opacity가 가장 안전합니다. filter·clip-path·SVG·background-color는 브라우저별로 가속 지원이 늘고 있는 중입니다. height·padding·top/left 같은 레이아웃 속성은 매 프레임 레이아웃→페인트→합성을 다시 돌립니다. web.dev 실험(2020)에서 top/left 이동은 프레임 약 50%, transform 이동은 약 1%를 드랍했고, Motion 공식 성능 문서도 지금 같은 원칙을 유지합니다.
    • 적용: c8c-web에서 animate/transition에 height·width·top·left·margin·box-shadow를 쓰는 곳을 grep해 transform: translate/scale과 opacity로 바꿉니다. 그림자 효과는 미리 그려 둔 ::after의 opacity를 바꾸는 방식으로 대체합니다.
    • 출처: https://motion.dev/docs/performance · 날짜 미상(2026-10 열람) / 대조 자료 web.dev animations-guide 2020-10-06 · 확신 high
  2. motion 최신 버전은 14.7.1(2026-10-27)이고 peerDependencies가 react ^18 || ^19라 React 18에서도 씁니다. v12(2025-01-20)는 React 쪽 breaking change 없이 패키지명만 framer-motion→motion으로, import 경로는 'motion/react'로 바뀌었습니다. v13(2026-08-05)은 선택 의존성 @emotion/is-prop-valid를 없애고 <MotionConfig isValidProp>로 직접 넘기게 했고, v14(2026-10-02)는 내부 API 정리입니다.
    • 적용: 브랜치에서 framer-motion@11.18을 motion@14로 교체하고 import를 'motion/react'로 일괄 치환합니다. 루트에 <MotionConfig isValidProp={isPropValid}>를 넣은 뒤 styled(motion.div)에서 DOM 경고가 나는지 확인합니다.

반론

  • Vercel 가이드는 'CSS > WAAPI > JS 라이브러리' 순서를 권한다. 그래서 #7 액션처럼 스크롤텔링 기본을 motion useScroll(JS)로 두면 이 가이드와 정면으로 어긋난다. CSS 우선에 JS 폴백이 가이드에 더 맞는다.
  • Figma Motion 스프링은 bounce 하나(0~1)로 정규화돼 있다. M3의 stiffness/dampingRatio 토큰을 Figma 변수로 왕복하면 값이 손실될 수 있으니, 정본은 코드 쪽 토큰 파일에 두고 Figma는 근사값으로 보는 편이 안전하다(변환 손실 정도는 미검증).
  • damping 환산이 맞아도 Compose와 motion은 정지 판정 임계값(visibilityThreshold와 restDelta·restSpeed)이 달라 체감 길이가 다를 수 있다. 또 motion에 duration이나 bounce를 함께 넘기면 stiffness/damping이 무시된다.
  • DTCG 2025.10은 커뮤니티 그룹 보고서라 도구 지원이 고르지 않을 수 있다. Style Dictionary 같은 변환기가 $extensions 스프링을 읽는지는 확인하지 않았다.
