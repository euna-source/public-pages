# 화면 경계를 정한 이유

## 가입 완료와 로그인 성공

현재 확인한 가입 흐름에서는 이름 입력 화면의 ‘회원가입 완료’ 버튼 뒤에 가입 성공 처리가 일어납니다. 독립된 가입 완료 페이지를 새로 가정하지 않습니다. 따라서 화면명은 ‘회원가입 · 이름 입력’이고 가입 성공은 별도 `sign_up` 이벤트입니다. 이후 실제로 나타나는 권한 안내·이용 안내·환영 영상·메인에 각각 해당 화면 이름을 사용합니다.

가입 뒤 다시 로그인 화면을 반드시 거친다는 순서를 만들지 않습니다. 가입 성공 시 인증 상태가 저장되므로, 신규 가입 경로와 기존 회원 로그인 경로는 서로 다른 흐름입니다. 딥링크나 기존 동의 상태에 따라 첫 목적지가 바뀔 수 있습니다.

## 마이와 타인 프로필

‘마이 · 프로필’은 내 커버·이력 중심의 화면, ‘크리에이터 · 프로필’은 다른 사람의 같은 화면입니다. 소개와 작업물 탭은 실제 전면 상태에 따라 별도 이름을 사용합니다. 프로필 상단 헤더와 하단 목록이 함께 보인다고 두 화면을 동시에 보내지 않습니다.

타인의 프로필 정보를 수정하는 기능은 확인한 소스에서 근거를 확보하지 못했습니다. 타인 흐름에는 프로필 열람·리스펙트·인맥·노크·대화를 정의했고, 프로필 정보 수정은 내 정보 또는 관리 권한이 있는 팀 정보에만 배치했습니다.

## 프로필 등록 폼의 내부 단계

커버 정보 입력 폼은 직업·ID·이름·한 줄 소개·표지·프로필 사진을 한 스크롤 편집 흐름으로 보여 줍니다. 자기소개 폼도 키워드·이미지·소개 글을 같은 화면 안에서 펼칩니다. 각각 하나의 화면명으로 기록하고 어느 입력 단계인지는 속성으로 구분합니다.

다만 폼에서 직업 검색·이미지 자르기 같은 독립 화면을 열면 새 화면입니다. Web의 커버 스타일 선택 페이지 역시 네이티브 입력 폼과 분리되어 있어 다른 이름을 부여했습니다.

## 소통과 협업

채티의 대화·라운지·프로젝트 목록은 전면 내용이 바뀌는 탭이므로 각각 정의합니다. 1:1·라운지·프로젝트·팀 대화방은 이용 목적과 관리 구조가 달라 분리합니다. 같은 방 안 메시지 전송·읽음·첨부 버튼 클릭은 별도 화면이 아닙니다.

프로젝트 콘텐츠 상세, 프로젝트 참여 신청, 지원자 목록, 프로젝트 대화방은 같은 기능 묶음에 속해도 서로 다른 화면입니다. 반대로 팀 정보 입력의 신규·수정은 같은 폼의 모드이므로 한 화면 이름을 유지합니다.

## 화면 이름을 만들지 않는 항목

| 항목 | 기록 방법 |
|---|---|
| 가입 완료·로그인 성공 | 성공 액션. 실제 후속 화면은 별도 조회 |
| 팔로우·북마크·좋아요·리스펙트 전송 | 해당 화면의 행동 이벤트 |
| 메시지 보내기·지원하기·초대 수락 | 성공·실패 행동 이벤트 |
| 저장 완료·작성 중단 | 작성 화면의 결과 이벤트 |
| 입력 칸·선택한 키워드·필터 값 | 현재 화면의 입력·상태 값 |
| 로딩·빈 목록·재시도 오류 | 같은 화면의 content_state |
| 부모 컨테이너·숨겨진 이웃 WebView | 독립 화면 조회 없음 |
| 확인 팝업·토스트·키보드·OS 권한창 | 앱 화면명 추가 없음 |

실제 진입을 확인하지 못한 예전 캐스팅·구형 온보딩·클럽 경로는 별도 보류 목록에 있습니다. 제품 화면이 실제로 열리는 것을 확인한 뒤 동일한 원칙으로 제목을 정의합니다.
