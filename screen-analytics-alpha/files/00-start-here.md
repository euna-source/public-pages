# 화면명 통합과 수집 개선 검토안

이 문서는 기획·개발·데이터 담당자가 같은 화면을 같은 이름으로 분석하도록 만드는 개발 전달안입니다. 먼저 팀 목록, 프로필, 검색, 콘텐츠 상세의 이름과 기록 조건을 맞추고, 확인된 수집 로직 문제를 고친 뒤 나머지 화면에 같은 규칙을 적용합니다.

예를 들어 ‘내 팀 목록’은 현재 Android에서 `contacts_team`, iOS에서 `team_list`로 기록합니다. 앞으로는 두 플랫폼 모두 `team_list`로 보내고, 분석 화면에서는 ‘내 팀·팀 초대 목록’으로 표시하도록 제안합니다. 첨부 미디어 미리보기와 제안 상세처럼 이름은 같아도 내용이 다른 경우에는 각각 나눕니다.

현재 문서는 소스를 근거로 작성한 개발 검토안입니다. 최신 알파 배포 성공 기록, iOS 실제 빌드번호, GA와 내부 데이터의 수신 결과는 아직 확보하지 못했습니다. 따라서 ‘최신 알파에서 정상 수집됨’으로 판정하지 않습니다.

| 확인한 기준 | 소스에서 확인한 값 | 남은 확인 |
|---|---|---|
| AOS | 3.1.0, Dev/Alpha 빌드번호 396, develop `b135a9414` | 해당 커밋의 수동 알파 배포 성공과 설치 APK 일치 |
| iOS | 3.0.2, alpha `34ad6c9db` | TestFlight 업로드 성공과 실제 빌드번호. 빌드번호는 배포 시 조회·발급하므로 소스 설정만으로 확정할 수 없음 |
| Front Web | alpha/2026.08.AS548 `de80fc8d2` | 해당 빌드의 수동 Alpha Deploy 성공과 실제 서비스 자산 일치 |

소스 기준을 고정한 시각은 2026년 9월 9일 00:09 KST입니다. 브랜치 최신 소스와 배포 완료 소스는 다를 수 있습니다. 배포 이력이 다른 커밋을 가리키면 그 차이부터 다시 확인합니다.

지금 우선 해결할 사항은 다음과 같습니다.

| 순서 | 문제 | 개발 완료 조건 |
|---|---|---|
| 1 | 같은 팀 목록이 두 이름으로 기록되고, AOS 첨부 미리보기는 Web 제안 상세와 같은 이름을 사용 | 의미가 같은 화면만 합산되도록 이름과 이전 값 대응 조건 적용 |
| 2 | Web의 1초 제한이 다른 화면 이동까지 막음 | 0.1초 간격 A→B 이동에서 A·B 각각 한 번 기록 |
| 3 | Web 체류시간의 시작 시각이 모듈 로드 시각에 고정 | 실제 보이는 시점부터 구간을 측정하고, 숨김·재진입·화면 종료 처리 |
| 4 | 앱·Web·내부 로그가 서로 다른 필드와 화면 범위를 사용 | 공통 이름, 방문 식별값, 기록 주체, 수신 계약을 함께 적용 |
| 5 | WebView 사전 로딩, 부모·자식 화면, 자동 수집이 조회 수를 늘릴 수 있음 | 화면이 실제 보일 때만 한 번 기록하고 같은 방문의 발신자를 하나로 제한 |

공통 목록은 184개 정의 행으로 구성했습니다. 이 중 157개는 주 화면 이름 제안, 19개는 레거시 진입 확인 대상, 8개는 별도 화면 조회를 올리지 않는 컨테이너·상태·구성요소입니다. 이 숫자는 실제 활성 화면 수나 정상 수집 화면 수를 뜻하지 않습니다. 플랫폼별 구현 차이는 각 행에 남겼습니다.

기계가 읽는 목록은 [screen-registry.alpha-proposal.json](screen-registry.alpha-proposal.json)입니다. 이전 GA 이름은 [ga-name-mapping.json](ga-name-mapping.json), 내부 분류는 [internal-name-mapping.json](internal-name-mapping.json)에서 대응합니다. 예를 들어 이전 finder 값도 AOS의 GalleryRoute와 iOS의 검색 복귀 발신 위치를 구분해 각각 gallery_home·finder_search로 대응합니다. 같은 문자열을 같은 화면으로 간주하지 않습니다. 이전 이름표는 현재 알파 소스와 발신 위치에 한정한 변환 제안입니다. 과거 전체 데이터에 일괄 적용하거나 변경 전후 방문 수가 같다고 가정하면 안 됩니다.

기획 담당자는 화면의 의미와 목록 경계를 확인합니다. 플랫폼 개발자는 기록 위치와 중복 방지를 구현하고, 백엔드·데이터 담당자는 수신 및 집계 구조를 준비합니다. QA는 테스트 빌드에서 실제 이벤트와 최종 조회 결과가 일치하는지 확인합니다. 담당자 이름과 적용 일정은 팀 배정 시 채웁니다.

Web의 시간 제한 교체(AN-03)와 가시성·방문 중복 처리(AN-04)는 함께 배포하고 검증합니다. 전체 화면 목록은 소스 기반 후보 정의이며, 플랫폼별 실제 탐색과 대조한 최종 확정이 필요합니다.
