한눈에

  • 결정: 내 포트폴리오에도 리스펙트 버튼과 개수를 표시하고, 본인이 누르면 리스펙트를 줄 수 없다는 안내를 띄웁니다.
  • 구현 방향: 보관함의 파일 표시명과 서버 저장명을 분리합니다. iOS는 원래 파일명, Android는 날짜·시간과 랜덤 코드 조합을 쓰되 정확한 형식은 다시 정합니다.
  • 진행 방향: 보관함의 공지 탭은 우선 숨기고 게시판 도입 때 다시 구성합니다. 게시판 배포일과 개발 범위는 추가 논의합니다.
  • 운영 기준: 명예의 전당 캠페인 개시 최소 하루 전에 앱을 배포해 안정성을 확인합니다. 첫 회차 대상·재수상·상금·홍보 일정은 추가 협의합니다.
  • 확인 한계: 전사에 화자·시각 표기가 없어 참석자, 발언자, 담당자를 확정하지 않았습니다. 원음과 녹음 메타데이터는 대조하지 못했으며 아래 근거 시각은 모두 미제공입니다.

내 포트폴리오의 리스펙트 표시

  • 현황: 자신에게 리스펙트를 줄 수 없다는 이유로 내 포트폴리오에서는 버튼을 숨겼습니다. 명예의 전당에서 받은 리스펙트를 집계하므로 내 작업물에서도 개수를 확인할 필요가 제기됐습니다.
  • 초기 제안: 아이콘·개수를 추가하고 누르면 리스펙트를 준 사람의 바텀시트를 연결하는 안이 나왔습니다.
  • 결정: 다른 사람의 포트폴리오처럼 버튼과 개수를 표시합니다. 자기 포트폴리오에는 리스펙트를 줄 수 없으며, 누르면 그 이유를 안내하는 토스트를 띄웁니다.
  • 목록 확인: 리스펙트를 준 사람은 기존처럼 상세 화면의 목록에서 확인합니다. 새 바텀시트 연결은 추가 확정하지 않았습니다.
  • 유지: 영감 좋아요의 기존 동작은 유지합니다. 리스펙트는 소진되는 반응이라는 점이 구분 근거로 언급됐습니다.
  • 후속: Android·iOS 양쪽 적용 가능 여부를 확인하고 안내 문구를 정리합니다.

명예의 전당 이벤트 페이지와 운영 조건

  • 페이지 구성: 배너와 배경 영상을 넣습니다. 회의에서 보여 준 영상은 최종본이 아니므로 교체를 고려합니다.
  • 콘텐츠: 설명·정보 아이콘 안내는 별도 데이터를 받지 않는 정적 콘텐츠로 구성합니다. 회차별 금액·조건은 이벤트 설명 페이지에서 안내하는 방향입니다.
  • 이동: 이벤트 페이지에서 명예의 전당으로 이동하는 링크를 제공합니다. 작품 등록은 기존 플러스 버튼을 사용합니다.
  • 구현 제안: 수정하기 쉬운 외부 페이지 활용과 화면 상단까지 웹으로 구성하는 안이 나왔습니다. 단순 등장 효과와 스포트라이트가 켜지는 연출도 논의했으나 최종 사양은 미정입니다.
  • 후보 없음: 후보자가 없는 화면을 추가합니다. 집계 중 안내가 예시로 나왔고, 문구와 노출 조건은 정리해야 합니다.
  • 1회차 대상 제안: 기간 내 업로드 작품만 보던 기존안에서 첫 회차에는 기존 작품도 포함하자는 의견이 나왔습니다. 포함 범위와 반응 집계 기준은 확정하지 않았습니다.
  • 재수상 이견: 같은 작품의 반복 수상을 허용하자는 의견과, 이미 수상한 작품을 제외해 다른 작품에 기회를 주자는 의견이 갈렸습니다. 운영하면서 판단하자는 발언이 있어 최종 규칙은 남아 있습니다.
  • 활동 점수 기준: 크리에이터 활동 점수는 해당 기간의 활동을 집계합니다. 과거 전체 누적 점수를 그대로 사용하는 방향은 배제했습니다.
  • 상금 문구: 150만 원이 언급됐으나 대표님과 추가 협의하기로 했습니다. 확정 금액으로 기록하지 않습니다.
  • 홍보: 공식 채널·커뮤니티와 관계자에게 이벤트 링크를 알리는 방안을 정리해 글로 공유하기로 했습니다. 구체적인 채널·방법은 미정입니다.
  • 배너 제안: 초기에 상단 노출 후 반복 방문자에게 아래로 내리는 안이 나왔습니다. 세 번 노출은 예시이며 최종 횟수·조건이 아닙니다.

보관함 화면과 파일명 처리

  • 화면 변경: 채팅방 메뉴에서 들어가는 보관함을 리스트형에서 썸네일 중심으로 바꿉니다. 링크의 오픈그래프 표시가 언급됐지만 정확한 규격은 확인이 필요합니다.
  • 표시명·저장명 분리: 실제 서버 파일은 난수 기반으로 저장하고, 사용자에게 보여 주는 이름은 별도로 관리하는 방향에 합의했습니다. 표시명을 받는 API 작업이 필요하다는 설명이 있었습니다.
  • iOS 방향: 원래 파일명을 표시하고 다운로드할 때도 같은 이름을 유지합니다.
  • Android 제약: 원래 파일명을 가져오기 어렵다는 개발 설명에 따라 별도 이름 생성 규칙을 논의했습니다. 해당 제약은 회의 발언 기준이며 실제 코드로 검증한 사실은 아닙니다.
  • 후반 정리안: 파일 종류 접두어를 빼고 날짜·시간 뒤에 랜덤 코드 네 자리를 붙이는 방향으로 모였습니다. 연도 자릿수·초 포함 여부·구분자·문자 종류는 예시를 포함해 다시 전달해야 합니다.
  • 대안 검토: 같은 이름 뒤에 1, 2를 붙이려면 페이지 밖 파일까지 중복을 확인해야 한다는 부담이 제기됐습니다. 전체 조회를 동반하는 방식은 채택하지 않았습니다.
  • 우선 기준: 파일들이 같은 이름으로만 보이지 않게 구분하는 것이 핵심입니다. 세부 이름 규칙 때문에 주요 기능 개발이 지연되지 않도록 공수를 고려합니다.
  • 다운로드: 화면에 보이는 이름과 다운로드 이름을 맞추는 방향입니다. iOS 원본명 중복과 Android 랜덤 코드 충돌 처리는 미정입니다.
  • 공유 상태: 로컬 DB로 구현한 자료실 알파 버전을 확인하고 피드백을 받기로 했습니다. ‘로컬 DB’는 전사 문맥 해석이며, 업로드 완료·진행 중 표현이 함께 나와 상태 확인이 필요합니다.

보관함 공지 탭과 게시판 도입

  • 문제: 현재 공지는 상세 화면·재공지·삭제 등 게시물 관리 기능이 없어, 보관함에 과거 공지 목록만 남기는 효용이 작다는 의견이 나왔습니다.
  • 진행 방향: 보관함의 공지 탭을 우선 숨기고 게시판이 생길 때 다시 구성합니다. 기존 채팅방 공지 기능 전체를 제거한다는 결정은 아닙니다.
  • 필요성: 프로젝트의 운영 규칙·자료·전달사항을 대화와 별도로 남길 게시판이 필요하다는 데 공감했습니다.
  • 범위 제안: 채팅방 전반의 게시판, 일반 참여자의 글 작성, 방장만 공지 지정, 대화를 게시물로 전환하는 안이 나왔습니다. 이번 구현 범위로 모두 확정한 것은 아닙니다.
  • 일정 논의: 중순 업데이트에 넣기 위해 기존 기능 일부를 빼는 안을 검토했으나, 남은 개발 시간이 짧고 게시판은 작성·조회·수정·삭제·첨부까지 작업량이 많다는 설명이 있었습니다.
  • 유지 의견: 답글 달기는 중요도에 비해 공수가 크지 않다는 의견이 있었고 제외를 결정하지 않았습니다. 사진·동영상 동시 업로드 등을 빼는 것으로도 충분하지 않다는 설명이 있었습니다.
  • 결론: 이번 회의에서는 게시판 배포일을 정하지 않았습니다. 10월 중순·다음 정기 배포·중간 별도 배포를 놓고 다시 논의합니다.

프로젝트 공유·알림 버튼과 위젯

  • 공유 버튼: 프로젝트·라운지 공유 버튼 위치를 양 OS에서 맞춥니다. iOS·Android의 현재 배치가 달라 디자인 정리가 필요합니다.
  • 배치 제안: 첫 화면에서 공유에 접근할 수 있게 하고, 알림은 토글 대신 벨 아이콘으로 표현하는 안이 나왔습니다. 공유·알림의 정확한 위치는 확정되지 않았습니다.
  • 위젯 방향: 포트폴리오 보기·올리기, 영감 올리기 등 개발 중인 바로가기 구성을 우선 적용하고 나중에 조정하는 데 동의했습니다. 기능별 정확한 이름은 티켓 대조가 필요합니다.
  • 위젯 일정: 10월 6일 배포분에 포함해야 한다는 발언이 있었습니다. 배포 티켓과 포함 범위를 확인해야 합니다.
  • 불명확한 말: 위젯 직전 ‘게임랭킹’처럼 인식된 표현은 별도 기능인지 알 수 없어 결정 항목으로 만들지 않았습니다.

디자인 공유와 앱 배포·캠페인 개시

  • 완료 보고: 지난주 공유한 일정에 CCO 티켓을 연결해 뒀다는 설명이 있었습니다. 제품 개발 메시지에서 확인하도록 안내했습니다.
  • 디자인 요청: 다른 작업과 섞인 10월 업데이트 디자인을 별도로 나누고 보관함·자료실·채팅방 검색을 정리합니다.
  • 공유 약속: 자료실을 제외한 나머지는 내일(9/29) 공유하고, 자료실은 내일까지 작업을 마쳐 내일 모레 수요일 오전(9/30)에 공유하는 일정에 동의했습니다. 공유물의 정확한 범위는 확인이 필요합니다.
  • 검색 확인: 채팅방 검색 디자인과 양 OS 알파 버전 동작을 확인하기로 했습니다. 검색 구현 담당은 전사만으로 특정하지 않았습니다.
  • 운영 기준: 캠페인 시작 최소 하루 전에 앱을 운영 환경에 배포하고 안정성을 확인해야 한다는 기준을 재확인했습니다.
  • 잠정 일정: 화요일 배포·수요일 캠페인 개시가 논의됐습니다. 10월 5일 휴일과 6일·7일 언급을 함께 보면 10/6·10/7로 해석되지만, 캠페인 날짜 자체는 유동적입니다.
  • 추가 확인: 교체가 지연된 노출 콘텐츠는 민석님에게 다시 확인하겠다는 발언이 있었습니다. 대상 콘텐츠와 실제 확인 담당은 미정입니다.
