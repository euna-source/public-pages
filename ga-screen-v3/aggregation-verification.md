# 화면 이름이 보고서의 숫자로 이어지는지 확인합니다

내 프로필에서 설정을 열고 계정으로 들어갔다가 설정으로 돌아오면, 설정 방문은 두 번입니다. 두 OS가 같은 이름을 보내도 보고서가 이 재방문을 지우거나 중복 전송을 더하면 이용 흐름을 잘못 읽게 됩니다. 이 안내는 원시 수신 기록과 실제로 사용할 보고서의 합계를 대조하는 방법입니다.

## 이번 데이터로 정할 일을 먼저 좁힙니다

첫 목적은 3.0의 두 OS에서 화면 이용을 같은 기준으로 읽는 것입니다. 방문이 많은 화면을 조사할 후보로 찾고, 설정에 처음 들어온 방문과 계정을 보고 돌아온 방문을 구별합니다. 화면 방문에는 저장 성공·실패의 의미가 없으므로 이 기록으로 정보 수정 성공률이나 가입 완료율을 만들지 않습니다.

질문·신호·계산식은 `measurement-plan.json`에 있습니다. 화면 이름과 허용값은 기존 `screen-contract.json`, 발생·미발생 조건은 `runtime-verification.md`와 `scenarios.json`을 함께 사용합니다. 이번 분석안은 사용자 결정인 두 OS 통일을 구체화한 제안이며, 화면별 의미 검토를 대신 승인하지 않습니다.

## 정상 재방문과 중복 전송을 구분합니다

아래는 양 OS가 각각 같은 네 조작을 했다고 가정한 계산 예시입니다. 실제 수신 결과가 아닙니다.

| 조작 | 이름 | OS별 기대 방문 수 | 직전 활성 화면 |
|---|---|---:|---|
| 내 프로필에서 기록 시작 | my_profile | 1 | none |
| 설정 열기 | settings_home | 1 | my_profile |
| 계정 열기 | settings_account | 1 | settings_home |
| 설정으로 뒤로가기 | settings_home | 1 | settings_account |

OS 하나에서는 총 네 번 방문하고 화면 종류는 세 개입니다. 두 OS 합계는 여덟 번이며 화면 종류는 여전히 세 개입니다. 설정은 OS별 두 번으로, 방문 비중은 2/4입니다. 그중 내 프로필에서 온 방문과 계정에서 돌아온 방문이 각각 1/2입니다. 이는 이 시험 실행의 구성 비율이며 고객 전환율이 아닙니다.

방문 ID는 새 방문마다 새로 만들어야 합니다. 같은 화면 이름을 한 번으로 합치지 않습니다. 같은 실행에서 같은 방문 ID를 재사용한 행은 지우지 말고 오류로 남깁니다. 두 번 전송하면서 ID까지 새로 만들면 ID 검사만으로는 못 찾으므로 기존 조작·수신 검사에서 기대 횟수도 대조합니다.

## 실제 사용할 보고서를 고정합니다

데이터 담당이 기존 GA 속성의 OS별 스트림, 대상 빌드, 시간대, 보고 시작·종료일, 조회 시각, 수집·내보내기 필터를 기록합니다. 현재 이 값들은 미확인입니다. 종료 경계는 ‘종료 다음 날 00시 미만’으로 맞추고, 분모가 0이면 비율은 계산 불가로 표시합니다.

대상 빌드의 모든 화면 조회를 먼저 가져와 이름·버전·필수 값 누락과 중복을 확인합니다. 오류 행을 먼저 걸러낸 자료로 정상 수신율을 계산하지 않습니다. 품질을 확인한 뒤 같은 빌드·기간 안에서 계약 버전 3의 화면별 방문과 직전 화면별 방문을 집계합니다. 미수집 화면은 이벤트 표만으로 발견할 수 없으므로 화면 도달 목록과 별도로 대조합니다.

자동 횟수 대조는 BigQuery의 원시 이벤트로 만든 보고서만 지원합니다. 연결돼 있는지 현재 확인하지 못했으므로 새 저장소·결제·연결을 만들지 않습니다. 연결이 없으면 아래 자동 대조는 대기이며, 권한 있는 담당자가 기존 GA 보고서의 정의·필터·실제 수신을 수동으로 비교합니다. GA 화면과 BigQuery는 가공 방식이 달라 숫자가 다를 수 있어, GA 화면 보고서를 이 도구에 넣어 완전 일치를 요구하지 않습니다. 임의의 차이 허용치로 통과시키지도 않습니다. [Google의 내보내기 설명](https://support.google.com/analytics/answer/9358801)

일일 테이블과 당일 임시 테이블을 중복해서 합치지 않습니다. 일일 테이블도 늦게 들어온 이벤트로 갱신될 수 있으므로 추출 시각과 재확인 결과를 남깁니다. DebugView에서 보였다는 사실로 운영 집계가 완료됐다고 올리지 않습니다. [Google의 테이블 갱신 안내](https://support.google.com/analytics/answer/9358801)

## 원시 수신과 보고서의 같은 실행을 대조합니다

1. `runtime-verification.md`대로 두 OS의 같은 시나리오를 실행하고 조작 녹화와 전체 수신 기록을 받습니다. 일반 수집을 검증할 때는 디버그 모드를 끈 별도 실행을 사용하고 속성의 필터 설정을 기록합니다.
2. BigQuery에서 실제로 사용할 집계 쿼리로 같은 실행·빌드·시간 구간을 고르고, OS·화면 이름·직전 활성 화면별 화면 방문 횟수를 CSV로 내보냅니다. 원시 CSV를 이 검사기로 계산한 파일을 ‘별도 보고서’라고 제출하지 않습니다. 원시 자료와 보고서가 같은 범위라는 점을 담당자가 직접 확인해야 합니다.
3. 보고서 CSV의 열은 `platform,screen_name,previous_screen,views`입니다. OS 값은 `ios,aos`이며, 화면 이름은 실제 이름 차원을 사용합니다. 빈 값·중복 그룹·음수·소수·누락 화면·추가 화면을 허용하지 않습니다. 영문 키를 GA 클래스 이름으로 대체하지 않습니다.
4. 보고서 CSV와 같은 이름의 JSON에 출처 종류·추출 시각·보고서 위치·동일 실행 여부와 파일 해시를 남깁니다. 형식은 내려받는 예시의 `report.json`을 참고합니다. 원시 수신을 변환했다면 변환 규칙과 원본 증거도 보관합니다.
5. 아래 검사를 실행하고, 보고서의 표와 원시 수신 화면을 직접 대조합니다.

```sh
python3 verify_aggregation.py 실행폴더 보고서.csv --scenario my_settings
```

검사는 먼저 조작·수신의 누락·중복·순서를 확인한 뒤 보고서 합계를 비교합니다. 해시는 파일이 바뀌지 않았는지 확인할 뿐, 담당자가 기입한 출처의 진실성을 입증하지 않습니다. 통과 범위는 선택한 시험 실행의 횟수 대조이며 전체 운영 집계의 완전성이나 릴리스 승인이 아닙니다.

입력 폴더에는 선택한 시나리오 집합의 완전한 조작·수신을 넣습니다. 선택 밖 시나리오가 섞이면 자동으로 걸러내지 않고 거부합니다. 여러 시나리오를 합친 파일은 포함된 각 시나리오를 `--scenario`로 모두 지정하고, 보고서도 같은 집합으로 내보냅니다. 선택한 실행 안에서는 구이름·미버전·중복·예상 밖 이벤트를 삭제하지 않습니다.

다운로드에는 합성 예시도 들어 있습니다. 이 예시에는 실제 사용자·기기·수신 데이터가 없으며, 시험 옵션 없이는 통과하지 않습니다.

```sh
python3 verify_aggregation.py examples/my-settings examples/my-settings/report.csv --scenario my_settings --test-fixture
```

## 확인한 증거만 상태를 올립니다

| 상태 | 필요한 증거 | 현재 |
|---|---|---|
| 정의 | 목적·발생 조건·계산식·화면별 의미 확인 | 초안 작성, 의미 검토 대기 |
| 구현·수신 | 해당 계약을 적용한 두 OS 빌드와 실제 조작·수신 | 미확인 |
| 보고서 집계 | 일반 수집 실행과 실제 보고서 대조, 기간·필터·누락 확인 | 도구 시험만 가능, 실측 미확인 |
| 실제 개선 | 데이터 오류·운영 부담 또는 고객 과업의 개선 관찰 | 미측정 |

오류가 나오거나 분모·빌드 구성이 달라지면 비교와 효과 해석을 보류합니다. 수집·계산을 고친 뒤 같은 조건으로 다시 확인합니다. 담당자와 기한은 현재 정해지지 않았으며 자동으로 채우지 않습니다.

운영 데이터에서 방문 ID까지 새로 만들어 중복 전송하면 ID 검사만으로는 판정할 수 없습니다. 대표 조작의 기대 횟수와 앱 호출 위치를 함께 확인한 범위를 밝히고, 일반 이용량의 분모는 그 검증을 적용한 명시 빌드·기간으로 한정한 분석값으로 남깁니다. 완전히 오류 없는 전체 고객 모집단을 확보했다는 뜻으로 쓰지 않습니다.
