작성·운영 기준

문서가 바뀌어도 기준은 남도록.

보기 좋은 양식과 정확한 내용은 함께 관리합니다. 누가 무엇을 결정했고 어디까지 구현·검증했는지 문서의 구조 안에 남깁니다.

모든 문서에 공통으로 필요한 것

필수 정보와 선택 모듈의 경계
공통 머리말 · 필수 본문 · 목적에 따라 선택
문서 제목과 목적 한 문장 문제 장면·배경·근거
이번에 정하거나 확인할 내용 범위·대안·비교·추천
정책·구현·검증 상태 규칙·예외·상태·문구·데이터
담당 역할·업데이트 날짜·적용 버전 운영 단계·진입/종료 조건
정본 링크와 변경 이력 인수 조건·측정·검증 증거

미결이 없으면 ‘미결 없음’, 담당자가 정해지지 않았으면 ‘담당 미정’으로 씁니다. 내용이 없는 섹션은 지우되, 중요한 질문을 검토하지 않은 상태와 혼동하지 않게 합니다.

확정·구현·검증을 한 단어로 합치지 않습니다

정책 상태
초안 → 검토 중 → 확정 → 대체·폐기. 확정에는 승인 근거와 적용 시점이 필요합니다.
구현 상태
미착수 → 진행 중 → 구현 완료. 연결 티켓이나 변경 근거가 필요합니다.
검증 상태
미실행 → 검증 중 → 통과·실패. 환경·빌드·확인 항목과 증거가 필요합니다.
‘확정’ 배지만으로 개발 완료를 뜻하지 않습니다정책이 확정됐어도 구현은 미착수일 수 있습니다. 구현이 끝났어도 검증은 실패일 수 있습니다. 상태는 각자의 근거로 바꿉니다.

작성 순서

  1. 01 / 독자

    읽은 뒤 해야 할 행동을 정합니다.

    결정, 구현, 운영, 항목 조회, 재현·검증 중 가장 중요한 목적 하나를 고릅니다. 다른 목적은 보조 모듈로 붙입니다.

  2. 02 / 내용

    사실·결정·제안·미결을 분리합니다.

    근거가 없는 내용을 확정 규칙처럼 채우지 않습니다. 핵심 값은 정본 한 곳에서 관리하고, 반복 구간에서는 ID나 링크로 참조합니다.

  3. 03 / 구조

    가까운 템플릿에서 필요 없는 부분을 덜어냅니다.

    한 섹션은 하나의 질문에 답하게 합니다. 문장은 본문, 속성은 정의 목록, 비교는 표, 순서는 단계형으로 표현합니다.

  4. 04 / 공유

    실제 내용으로 확인한 뒤 버전을 남깁니다.

    새 규칙을 추가하면 관련 예외·상태·인수 조건도 같이 살핍니다. 제목 변경으로 앵커가 깨지지 않도록 안정된 ID를 유지합니다.

공유 전 검수

외관만으로 확인할 수 없는 항목도 따로 남깁니다.
검수 영역 확인 질문
내용·정보 구조 첫 화면에서 목적·현재 상태·다음 행동이 보이나요? 규칙과 예외가 연결되나요? 같은 숫자가 충돌하지 않나요?
텍스트·시각 제목만 읽어도 흐름이 있나요? 본문이 너무 길거나 작지 않나요? 강조가 한곳에 몰리지 않나요?
두 테마 텍스트·상태·선택·초점·입력 경계가 두 모드에서 보이나요? 스크린샷과 삽입 이미지의 밝은 배경도 확인했나요?

조작·접근성 키보드와 터치로 사용할 수 있나요? 조작 이름·필드 라벨·표 헤더·초점 복귀·오류 안내가 있나요?

전달·운영 비로그인 링크가 열리나요? 링크·폰트·파일·인쇄가 동작하나요? 민감 정보는 없나요? 정본과 변경 이력이 있나요?

기존 문서에 적용하는 순서

먼저 적용할 범위

  1. 명예의 전당의 운영 한 구간
  2. 베스트 크리에이터의 규칙·예외 한 묶음
  3. 알림·토스트의 목록과 상세 한 세트

확인할 독자 과업

  • 이번에 결정할 것과 미결을 찾기
  • 특정 규칙의 예외와 적용 시점 찾기
  • 문구 ID로 항목과 변경 이유 찾기
  • 구현 완료와 검증 통과를 구별하기

실제 개발자·QA의 탐색 시간, 오해한 내용, 다시 질문한 항목을 기록합니다. 개선이 확인된 구조부터 넓혀 갑니다. 실제 문서의 분량이 커지면 긴 목록의 필터·상세 경로·성능을 추가 검증해야 합니다.

작게 유지하고, 근거를 남깁니다

새 에셋 추가
기존 에셋으로 해결되지 않는 반복 사례가 있을 때 제안합니다. 사용 목적·금지 상황·두 테마·모바일·상태·키보드·코드 예시를 함께 제출합니다.
변경 관리
기존 문서의 의미나 조작을 바꾸면 호환성 영향을 적습니다. 없앨 에셋에는 대체 경로와 유예를 알립니다. 승인 역할은 팀이 지정합니다.
정본 관리
문서 버전과 라이브러리 버전을 따로 기록합니다. 과거 링크와 요구사항 ID를 유지하고, 바뀐 부분은 이력에서 찾게 합니다.
공개·보안
공유 링크를 공개할 때 내부 경로·토큰·개인정보·미공개 사업 내용을 확인합니다. 공개 예시에는 가상 데이터를 사용합니다.

이번 버전의 제공 범위

정적 HTML·CSS·JavaScript로 된 문서용 키트입니다. 테마 선택·검색·복사·접기·대화상자는 실제로 동작합니다. 서버 저장, 협업 편집, 권한 처리, 실제 제품 기능은 구현하지 않습니다.

검증을 구분해 읽어 주세요자동 브라우저 검사와 화면 검수는 레이아웃·조작 결함을 찾는 데 사용했습니다. 실제 개발자의 이해도 시험, 실기기·Safari·스크린리더 종합 검증은 별도입니다. 기존 사업 문서는 아직 바꾸지 않았습니다.

무엇을 참고했고, 무엇을 다르게 했는가

  • IBM Carbon · Typography
    표현적인 제목과 생산성 중심 본문을 구분하는 원칙을 참고했습니다. 업무 검토 문서는 본문 15–16px와 별도의 읽기 폭을 제안합니다. 이 수치는 해당 문서용 제안이며 인용한 시스템의 공통 의무값이 아닙니다.
  • IBM Carbon · Color, Vercel Geist · Colors
    색을 역할과 표면 단계로 관리하는 접근을 반영했습니다. C8 브랜드 색을 그대로 본문 링크에 쓰지 않고 대비를 확보합니다.
  • Linear, Stripe
    명확한 글자 대비와 공간의 질서를 참고했습니다. 홈페이지의 큰 마케팅 연출을 장문 개발 문서에 그대로 옮기지는 않습니다.
  • GitHub Docs · Content model, Diátaxis
    독자의 과업에 맞게 문서 유형을 구분했습니다. 이번 키트의 다섯 템플릿은 해당 서비스의 공식 분류가 아닌, 현재 업무에 맞춘 제안입니다.
  • USWDS · Table, GOV.UK · Accordion
    비교 관계를 보존하는 표와 필요한 곳에만 쓰는 접기를 참고했습니다. 핵심 예외는 접지 않습니다.
  • MDN · prefers-color-scheme, MDN · color-scheme
    시스템 선호 감지와 브라우저 기본 조작부의 테마를 함께 반영합니다.
  • W3C · Reflow, Contrast, Target size
    반응형·대비·조작 영역의 검증 근거입니다. 가이드 구현만으로 전체 WCAG 준수를 인증하지 않습니다.
  • Pretendard
    글꼴은 SIL Open Font License로 동봉했습니다. 라이선스 원문
