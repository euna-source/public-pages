01정한 것

이번 버전은 그대로, 정본은 시험부터

항목 내용
이번 버전 이미 진행 중이라 기존 방식(Figma·문서)으로 마칩니다 (유재욱)
정본 방식 26.46.0 빌드(11월)부터 먼저 시험하고, 결과를 보고 다시 논의합니다 (유재욱 제안, 송하민 동의)
02제안

코드에서 뽑은 정본 하나를 모두가 봅니다

  • 유재욱의 제안입니다.
    Bitbucket의 iOS·Android·API 코드를 읽어 정본을 만들고, 화면은 바이브 코딩으로 만든 뒤 세밀한 부분만 Figma에서 다듬습니다.
  • 기획이 바뀌면 정본을 갱신하고, 각자 앱에서 달라진 부분만 받습니다.
    버전마다 변경 사항 목록이 나와 클라이언트는 화면을, 백엔드는 추가된 API를 확인합니다.
  • 목표는 한 팀을 빠르게 하는 게 아니라 일정 확인, 요구 조건 누락, QA 공수를 줄이는 것입니다.
    스타일 가이드를 정본에서 한 번 바꾸면 전체에 반영되는 점을 가장 큰 이점으로 꼽았습니다.
03화면 기준

API·UI 기준에 흐름도와 빈 상태가 더해졌습니다

  • 유재욱은 화면마다 API와 UI 기준만 있으면 된다고 봤고, 권태환은 흐름도가 중요하다고 했습니다.
  • 송하민은 AI가 흐름도를 읽을 수 있어 좋다며, 목록이 비었을 때 같은 빈 상태 화면도 필요하다고 짚었습니다.
    이런 화면은 기획자가 챙겨 만듭니다.
  • 유재욱은 AI에 요청할 범위를 너무 넓거나 세밀하게 잡으면 엉뚱한 결과가 나온다고 주의를 줬습니다.
04개발 쪽 의견

장점은 인정하고, 이중 작업을 걱정합니다

  • 임민석(백엔드)은 Figma에서 놓치는 부분을 잡는 장점은 있지만, 백엔드는 무엇으로 받든 큰 차이가 없다고 했습니다.
  • 임민석은 AI가 아직 부정확해 클라이언트가 먼저 개발하면 두 번 작업이 생길 수 있다고 했습니다.
    이중 작업을 받아들일 수 있다면 API 스캐폴딩부터 하자고 했습니다.
  • 송하민(iOS)은 화면 이름이 분명한 점이 Figma보다 낫고, 컴포넌트 재사용 문제는 기술적으로 풀어 뒀다고 했습니다.
    Figma로도 두세 번 작업한 적이 있으니 11월에 시험해 보자고 제안했습니다.
  • 유재욱은 열 번 중 두 번 틀리는 정도면 진행하자는 기준을 냈고, 새 페이지의 API 정리가 개발 PRD가 될 수 있다고 봤습니다.
05운영

기준은 배포된 서비스, 당분간 기존 관리 유지

  • 정본의 기준은 지금 배포된 서비스 버전으로 잡자는 게 유재욱의 의견입니다.
  • 자동 갱신이 안정될 때까지는 기존 관리 방식을 유지합니다.
  • 웹뷰로 띄우는 웹 페이지는 정본으로 만들기 어렵습니다.
06그 밖에

키즈 버전과 가입·프로젝트 화면 얘기가 나왔습니다

  • 키즈 버전(로 들림)이 들어가면 정본이 두 배로 늘지만 스타일만 바꾸면 된다고 유재욱이 봤습니다.
    권태환은 같은 계정에서 색만 바뀌면 문제가 생길 수 있다고 했고, 송하민은 아예 분리하자고 했습니다.
  • 권태환은 회원가입에서 여전히 무슨 앱인지 모른 채 가입부터 시킨다고 지적했습니다.
  • 이은희는 프로젝트 북마크·설정 개선과, 비가입자도 프로젝트 게시물을 보게 하고 댓글은 빼는 방안을 냈습니다.
